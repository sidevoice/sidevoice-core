# Conversation flow protocol (task T)

This is the core contract for the voice, connector, web, desktop and playground implementations of [sidevoice/.github#19](https://github.com/sidevoice/.github/issues/19). It describes the wire shape implemented by this branch. Consumers should pin a full core source SHA while developing together. These fields are part of one protocol change; no old client fallback is promised.

## Identities and ordering

- `thread_id` is the conversation. `epoch` is a `u64` local to that conversation, initially `0`. Core advances it exactly once when it accepts a qualified spoken turn start, including a turn that later ends empty. Focus, typing, skip, output settings and reconnect do not advance it.
- `revision` is the existing per-call routing boundary. It is retained on all frames. It does not authorize moving a reply to a newer epoch or session. Socket `seq` remains the resume cursor. Journal `seq` remains the history/pull cursor.
- `turn_id` identifies one device turn within `session_id`. Repeated starts do not advance the epoch again. A turn's target is captured at start; its pause and final transcription remain open until its terminal result. For offline turns, the finished frame must carry `offline: true`, the captured `thread_id`, and the focus `binding_id`; core assigns the epoch once on acceptance. An offline finish for an already open identity uses that turn's captured epoch/target; a completed or cancelled identity cannot be reopened.
- One `utterance_id` names one publication. A retry with the same content and context returns its original admission disposition. Reuse with different content or context is terminally refused. Publication order determines the order of `voice-reply` frames to each eligible session; same-epoch replies are not replaced.

## Device to core

A call hello may include `data.speech: {"on": true}` or `{ "on": false, "reason": "voice_off" | "agents_muted" }`. The reliable `voice-speech` frame has `data: {session_id, client_msg_id, on, reason?}` and is acknowledged by the ordinary client-message acknowledgement. Mic mute is independent of this output setting. Core accepts only `voice_off` or `agents_muted` when `on` is false.

`voice-user-turn` keeps its existing `started`, `finished`, `cancelled` phases, `session_id`, `client_msg_id`, and `turn_id`. Every online `started` frame must carry `data.thread_id` and `data.binding_id` supplied by the app for that voice call's conversation and captured focus binding, even if HTTP focus selection has moved meanwhile. Core resolves that pair against this call's current or recent focus identities, advances only the captured conversation epoch, and pins that target for the terminal frame. A missing pair is `room.request_invalid`; an unknown pair is `room.focus_changed`; reuse of an open `turn_id` with a different pair is `room.message_conflict`. A start before the call has any focus explicitly carries both fields as empty strings and has no conversation epoch. A finished offline turn additionally supplies `offline: true`, its captured `thread_id`, and focus `binding_id` (the ID in the selected focus view, not the connector's `binding.register` ID). On a **cancelled** frame, `merged: true` transfers an empty-turn obligation to the continuing turn. On a **finished** frame, `merged: true` means its `text` already includes the earlier merged turns; core queues those words once and does not transfer them away. Core answers a start with `voice-user-turn` carrying `revision`, `epoch`, and `thread_id`. A typed message uses `/api/presentation/text`; its receipt includes the current `epoch` without incrementing it.

### Focus changes during transcription and merge

The app runs one voice call per conversation and routes microphone input to the focused call. The app knows each call's conversation and captures its focus `binding_id` when that call's source turn starts. It tags that turn's `voice-user-turn.started` with the captured `thread_id` and `binding_id`; voice does not supply either identity. The app retains `turn_id -> {session_id, thread_id, binding_id, epoch/revision from core start}` until the turn's terminal event. Changing focus does not finish or discard a pending transcription. A's words are sent when A's normal end-of-turn fires, even if B is focused by then; they are not flushed merely because focus changed.

Each call's terminal event is routed using its captured target and contains only that call's turn transcript. Merging, when available, stays within the same conversation call: `cancelled` with `merged: true` transfers an empty-turn obligation to a continuing turn in that conversation, and `finished` with `merged: true` sends its already merged words once. A merged cancellation must never transfer A's obligation to B. For A pending in STT, focus B, then B speaks, core receives separate terminal `voice-user-turn` frames: A's `turn_id` with A's words to A at A's normal end-of-turn, and B's `turn_id` with B's words to B. Their arrival order may differ; each uses its original captured target. Core needs no additional capture or merge field on its wire frames.

`voice-playback` supplies the physical playback `utterance_id`, `status`, optional `reason`, and optional diagnostic `heard_chars`. Its status and cause control audio lifecycle and history diagnostics only. Neither field decides what the agent learns about hearing. A client also sends the reliable `reply-hearing` frame for its semantic delivery decision, including a reply that was written while audio output was unavailable:

```json
{"type":"reply-hearing","data":{"session_id":"SESSION","client_msg_id":"STABLE_ID","history_id":"HISTORY_ID","utterance_id":"REPLY_OR_REPLAY_ID","outcome":"partial","heard_chars":2}}
```

`history_id` identifies the assistant row; `utterance_id` is the original publication ID or a valid manual replay ID. The pair must identify the same retained row. An active authenticated call may acknowledge an original retained assistant row visible in history even when its audio focus is another conversation or it has never focused that row's conversation. This does not move focus, enable audio, or prove the page actually presented the row; the app sends the receipt only under its presentation policy. A manual replay receipt still requires that replay to target the reporting session. An absent call, missing row, or mismatched identity is refused as stale. `outcome` is exactly `heard | partial | not_heard`. `partial` requires `heard_chars`, a **positive** Unicode-scalar prefix strictly shorter than the full text. `partial` with zero is refused as `room.receipt_invalid`; use `not_heard` for a confirmed zero. `heard` means the full text; `not_heard` means zero confirmed characters. Omit `heard_chars` for those two outcomes. A reply with no audio target, including `text_only` in reading mode, can use its original `utterance_id` and history row ID. The app chooses the outcome from its physical result and local policy; skip, mute, disconnect and focus are never semantic hearing values. One stable `client_msg_id` makes retries idempotent. A later stronger acknowledgement can increase the cross-device maximum but never reduce it.

Before any terminal semantic receipt, history reports `hearing: null`, `heard_chars: null`, and `hearing_unconfirmed: true`; a missing receipt does not assert `not_heard`. Confirmed outcomes set `hearing` and `heard_chars` (zero for `not_heard`), and clear `hearing_unconfirmed` once no other outstanding target can raise the result. This flag is diagnostic history metadata, not a fourth agent fate. Only confirmed semantic facts enter agent evidence. An unconfirmed row may age out of the bounded journal without becoming a not-heard fact; a receipt after eviction is refused as stale.

### App playback reporting to core

The voice handle ID is local to the voice engine. Each app records the association between the core `voice-reply.data.utterance_id` and the handle ID returned by `say()` for that conversation's call, then sends the **core** ID in `voice-playback`. Core recognizes playback `status: playing | heard | interrupted | unplayed | failed`. Unknown status values have no effect. The handle's heard extent is a Unicode scalar count; preserve it as a nonnegative integer no larger than the original text's scalar length. A JavaScript UTF-16 offset must be converted before sending (for example, count code points in the prefix). A genuine played interruption may have `heard_chars: 0`; never convert it to `unplayed` merely because its confirmed prefix is zero.

Accepted diagnostic `voice-playback.reason` values are `user_interrupted`, `newer_turn`, `focus_changed`, `call_ended`, `unheard`, `agents_muted`, `voice_off`, `connector_disconnected`, and `heard_elsewhere`. Unknown reasons are treated as absent. An omitted diagnostic cause stays null; core does not invent a barge-in or newer-turn cause for a local stop. `status: failed` records `playback_failed` as audio history only. An explicit skip remains a local app action; it has no core reason, status, notice, or fate of its own.

| Per-call handle outcome or app action | `voice-playback` to core | Context |
| --- | --- | --- |
| `playing` event | `status: "playing"` | Send when sound starts. |
| `heard` | `status: "heard"` | Physical playback completed; the app still sends its semantic `reply-hearing` decision. |
| `heard-up-to`, app qualified a turn | `status: "interrupted", reason: "user_interrupted", heard_chars` | The person qualified a turn while sound was playing in this conversation. |
| `not-played`, app qualified a turn | `status: "unplayed", reason: "newer_turn"` | Accepted reply never sounded before the qualified turn. |
| `heard-up-to` or `not-played`, `cancelled` | `status: "interrupted"` or `"unplayed"`; diagnostic reason when available | The app separately chooses its `reply-hearing.outcome`; cancellation itself does not determine hearing. |
| `heard-up-to` or `not-played`, `stopped` | `status: "interrupted"` or `"unplayed"`; reason from the local action | Use `voice_off`, `agents_muted`, `call_ended`, `connector_disconnected`, or `focus_changed` as applicable. |
| `heard-up-to` or `not-played`, `failed` | `status: "failed"`, `heard_chars` when supplied | Core stores reason `playback_failed`; the voice failure `code` remains a local diagnostic. |

Send the terminal playback report and its `reply-hearing` decision before the final `voice-user-turn` message in the app's ordered reliable outbox for that call. The server's `client_msg_id` deduplication prevents the same reliable frame being applied twice; core compares semantic evidence so repeated reports cannot create two notices. Use one stable `client_msg_id` per frame when retrying. IDs are remembered for the bounded recent-device window (256 messages); completed turn identities are retained for 4,096 turns and publication identities for 2,048 admissions. After those windows, do not replay an old action as a new request.

The fixtures in [docs/fixtures/conversation-flow.json](fixtures/conversation-flow.json) spell out physical playback, independent semantic hearing, played zero extent, merged phases, and the complete offline frame. Core's fixture test checks the accepted mapped receipts and outcomes.

## Core to device

`voice-reply.data` contains `session_id`, `utterance_id`, call `revision`, `reply_revision`, conversation `epoch`, `thread_id`, `history_id`, `text`, and optional `language`/`replay`/`requested`. `voice-reply-withdrawn` remains explicit and names all affected `utterance_ids` and a reason. A client must stop a withdrawn reply and report its actual extent or never-started fate. It must not start a previously received reply after reconnect. Core does not replay missed `voice-reply` frames.

History rows include `epoch`, diagnostic `audio_reason`, semantic `hearing`, `hearing_unconfirmed`, `heard_chars`, `globally_heard`, and `replayable`. The semantic fields are derived only from `reply-hearing`, never an audio stop cause. Sidevoice-only notices have `role: note`, `text: ""`; they are system facts, not speech bubbles attributed to the person. Participant views include current `epoch`, `unheard: {count, since} | null`, and `working: bool | null`. Working is a fact only: the web applies the three second display delay.

History returns the most recent 1,000 retained rows plus any older retained globally unheard assistant rows. Those older rows stay visible for explicit manual replay until the bounded room journal can safely evict them. A client retaining older assistant rows refreshes their identities with `GET /api/presentation/history?thread_id=<thread>&resolve_id=<id>`; `resolve_id` may repeat up to 64 times per request. With at least one `resolve_id`, the response adds `resolved` (full current history rows for found IDs, even when absent from `messages`) and `missing_ids` (requested IDs no longer retained in that thread). Only explicitly resolved IDs are authoritative for replacement or removal; absence from `messages` alone is not. Each ID is 1–256 bytes; invalid requests return `room.request_invalid`. After another device confirms full hearing of an old miss, `resolved` carries its current `hearing`, `globally_heard`, `heard_chars`, and status so the client can remove the false unheard marker.

## Core and connector

`binding.register` returns `epoch` and `initial_reply_context: {thread_id, session_id, revision, epoch}` for speak-first. In that initial context, `session_id` is `binding:<binding_id>` and `revision` is `0`; use the returned values as issued. After input arrives, use that input's session, revision and epoch. Invented session IDs are refused. `speech.publish` requires `event_id`, `utterance_id`, `binding_id`, `session_id`, `revision`, `epoch`, and `text`; `history_only: true` records a request held across a connector outage without speaking it. A current-epoch reply while any captured turn is open returns terminal `status: rejected`, `reason: user_speaking`, `error: room.user_speaking`, and the wait instruction. It has no assistant row. The V3 RPC result echoes `event_id` and `utterance_id` even on refusal, so a connector can retire its outbox item. A stale epoch is written as `text_only` and is never spoken; its operational cause is available only as diagnostic history metadata. A future epoch is terminally refused. An identical retry retains the first disposition even if playback later changes. A saved `text_only` publication result has no hearing fate or cause field. Output settings and delivery policy cannot be inferred from that result.

For a `speech.publish` request whose response is uncertain, call V3 RPC `speech.recover` with **every original `speech.publish` field unchanged**, plus `recovery_binding_id` naming a currently live binding for the same connector and conversation. In particular, retain the original `binding_id`, `history_only` value, `session_id`, `revision`, `epoch`, `event_id`, `utterance_id`, `text`, and `language`; do not change `history_only` to repair uncertainty. Core checks the original fingerprint and returns the first saved or terminally refused disposition if it exists. If it does not exist, core atomically saves the text as `status: text_only`, `text_saved: true` and never emits late `voice-reply` audio for that attempt. The response echoes the two IDs exactly as `speech.publish` does. A conflicting ID/fingerprint is terminally refused as `room.speech_conflict`; an absent or stale recovery binding returns `status: unknown_binding` and must be re-registered before retry. The connector may retire an attempted outbox item only after a saved or terminal refusal response with matching IDs; a transport failure or `unknown_binding` leaves it pending for another recovery call. Once retired, fresh-context publications use their own original fields and can play normally. This is process-local recovery within the documented publication identity retention window.

Push `input.deliver` and pull `input.pull` carry the same content fields: `message_id`, `session_id`, `revision`, `epoch`, `channel`, `text`, optional `notice`, and optional `unheard`. Push also carries `event_id`, `binding_id`, and `thread`; pull carries `arrival_time` and `cursor`. `channel` is `voice` for the person's spoken or typed words and `note` for Sidevoice-only messages (`text: ""`). A notice does not create an epoch. Pull claims a note until its `message_id` is acknowledged or the claim is released, exactly as for user words. Push retries use the same row and message ID. A user input carrying `notice` does not expire before acknowledgement. If channel closure or a terminal push result prevents its delivery, core queues the full evidence as a new `channel: note` message with `notice.related_message_id` naming the original user message. For one conversation, push holds later messages behind an earlier pending retry; pull returns journal order.

Example confirmed not-heard evidence (the full text is retained so the agent can respond if relevant):

```json
{
  "message_id": "...", "session_id": "...", "revision": 4, "epoch": 2,
  "channel": "voice", "text": "Wait, another point.",
  "notice": {"kind": "reply_not_heard", "instruction": "Use the confirmed hearing extent and current context; respond again if still relevant."},
  "unheard": {"count": 1, "replies": [{
    "utterance_id": "...", "history_id": "...", "session_id": "...",
    "revision": 3, "epoch": 1, "text": "The original full reply.",
    "fate": "not_heard", "heard_chars": 0
  }]}
}
```

A confirmed partial reply has `fate: "partial"` and a `heard_chars` prefix strictly shorter than the full text; the remaining suffix stays in the full `text` field for agent context. No `reason` or `cut` is sent to the agent. A lost or missing semantic receipt does not produce `not_heard` evidence. `hearing_unconfirmed` remains history metadata until semantic evidence arrives.

Notice kinds are `reply_not_heard`, `turn_empty`, `user_returned`, and `reply_heard`. There is no skipped notice or fate. An envelope becomes permanently frozen when core first offers it to push `input.deliver` or includes it in a pull `input.pull` response. A failed push acknowledgement or released pull claim returns it to the queue with the **same `message_id` and payload**. Before first exposure, core may reconcile its hearing evidence in place: a confirmed `not_heard` reply stays in the untold batch, a stronger `partial` extent updates it, and only confirmed `heard` removes it. If that removal empties a `turn_empty` note, core keeps the same note ID and instruction because the no-words/refused-reply obligation still exists; it removes only the obsolete `unheard` data. An ordinary miss-only note with no replies left is suppressed. After exposure, an increased confirmed hearing extent generates a new `channel: note`, `notice.kind: reply_heard` with `notice.corrects_message_id` and `notice.heard: [{utterance_id, history_id, fate: "partial" | "heard", heard_chars}]`. Corrections only increase the cross-device maximum; late weaker original or replay reports cannot undo them. A reply already placed in an evidence envelope is never queued again as a fresh ordinary miss solely because its confirmed prefix increases. A no-words turn still queues `turn_empty` with the resend-if-relevant instruction. Return notices are queued after five seconds of eligible silence when confirmed untold misses remain. A late receipt that confirms a miss while no call on the conversation can hear it (none connected with speech on) queues nothing: the misses wait and the person's return delivers them in one `user_returned` notice, so the agent is not invited to answer into an empty call. Each evidence envelope contains at most eight full replies in publication order; extra batches are correlated ordinary notices. Consumers split text by Unicode scalar count, never by UTF-8 bytes or UTF-16 code units.

A late receipt after an empty turn becomes an immediate ordinary note. When a newer spoken message remains in the journal, `notice.related_message_id` links its follow-up; if bounded terminal history has already aged out, the late note still carries full reply evidence with `related_message_id: null`.

The in-memory room retains at most 2,048 conversation epoch identities. After that limit, admission of a previously unseen conversation returns `room.input_backlog_full`; an existing identity never silently restarts at epoch zero. Starting a turn reserves queue headroom for its possible notice and can also return `room.input_backlog_full`. These limits protect deferred notices as well as ordinary input.

Manual replay uses `/api/presentation/replay` and a new playback ID linked to the original history row. Returning alone never requests it. Replay is refused while output is off or a user turn is open.

The `reply-hearing.utterance_id` for a manual replay remains valid for a delayed reliable semantic receipt across park/resume of the **same session**. Park may first mark that replay interrupted; a later full or partial semantic receipt still updates the original row's aggregate hearing and sends any needed `reply_heard` correction for an exposed notice. Core retains up to 256 recent replay receipt identities in total, with at most 16 active; older finished identities and those belonging to a session that has left can no longer accept receipts. A replay ID already in use is refused with `room.stale_utterance`. An original reply's ID also remains available for late receipts while its history row is retained. No receipt causes automatic replay.

A reply sent to a call that is gone (its session ended, or parked while the page took a new one) is still heard when the same device's app played it from its call, which never ended: the app keeps and plays every reply it already holds, in order, and its `voice-playback` and `reply-hearing` receipts, sent under the device's new session, are accepted and count for the earlier call's share of the reply (`hearing_expected`). Only the device that was sent the reply can stand in for it. A person who left and came back holds nothing: their return is the `user_returned` note, as before. A core that restarted has lost its history, so receipts for replies of before the restart are refused with `room.stale_utterance`, which the app ignores.
